## Secrets and data

- !IMPORTANT: NEVER put credentials, tokens, API keys, server URLs or usernames of real servers in code, tests, examples, plans or docs.
- !IMPORTANT: Server passwords and tokens are stored only in the system keyring (`storage::credentials`, `keyring-core`: Secret Service on Linux, login keychain on macOS) - NEVER in `settings.toml`, `queue.bin`, caches or any other file.
- !IMPORTANT: NEVER use real user data (server addresses, usernames, library contents, listening history, YouTube accounts) in code, tests, fixtures or examples - use fictitious values (`http://navidrome.example`, `https://jazz.example.com/stream`).
- NEVER log credentials, passwords, tokens, salted Subsonic auth parameters, cookies, pairing tokens or full stream URLs that carry credentials. Mask or omit them.
- `.env` files are never read or committed. The app reads no `.env`; the live test environment is generated by `scripts/live-servers.sh` under `target/`.

## Remote control

- !IMPORTANT: Remote control is off by default (Settings > Integrations > Remote control). NEVER enable it by default or start the listener while it is off.
- !IMPORTANT: The host accepts connections only from local-network peers (`is_lan_peer` in `crates/remote/src/lan.rs`, checked by `host.rs` and discovery: loopback, private, link-local, unique local). NEVER widen this check.
- A new device needs an explicit approval on the controlled player (with a timeout), then proves itself on every connection with a challenge on a SHA-256 of its pairing token (`pairing::proof_of` / `proves`, random nonce). Pairing tokens are stored in `data_dir/remote-devices.json`; NEVER send the token itself over the wire after pairing.
- Traffic is not encrypted, so it carries only metadata and commands - NEVER passwords, credentials or stream URLs. Server songs move between players only when both use the same server (URL and user); the receiving player streams them with its own credential.
- Messages are newline-delimited JSON decoded into typed enums; unknown or malformed messages are rejected, never interpreted loosely.

## YouTube

- `yt-dlp` is an external program started with an argument list (`tokio::process::Command`) - NEVER through a shell, and NEVER with arguments built by concatenating user input into one string.
- Browser cookies exported by `yt-dlp` go to `$XDG_RUNTIME_DIR/feishin-rs` (`$TMPDIR/feishin-rs` on macOS) and are deleted right after reading. NEVER copy them into the config, cache or logs.
- YouTube tracks are never scrobbled or synced to the server play queue.

## Input handling

- Validate everything that comes from outside at the boundary: server responses are decoded into typed structs in the client crate (missing optional fields default, malformed responses become an `ApiError`), files on disk are decoded and versioned in `crates/storage`, remote messages in `crates/remote`.
- !IMPORTANT: NEVER concatenate input into shell commands, file paths or URLs - build URLs with `reqwest`/`url` query APIs and percent-encoding, and file names from ids you generate or hash (cover cache), never from server-provided names.
- A server, a lyrics provider or YouTube can return anything: NEVER index or `unwrap` into their data, and bound what you keep (paging, LRU caches).

## Network

- HTTP goes through `reqwest` with rustls. NEVER disable certificate verification.
- Calls to servers and external services run off the UI thread with timeouts, and their failures reach the user through `AppState.status` or a log line - never a crash.

## Dependencies

- Prefer well-maintained crates with licenses compatible with GPL-3.0-only (MIT, Apache-2.0, BSD, MPL, GPL). Justify any new dependency and add shared ones to `[workspace.dependencies]`.
